# Transcript format

The contract between speech recognition, the two-channel merge, and note
generation. Version `1`. Validated on load by `mt.transcript` — every error names
the offending field and index, because a schema error that slips through surfaces
later as a note that quietly misses the middle of a meeting.

## Shape

```json
{
  "version": 1,
  "meeting": { "title": "Billing migration weekly", "date": "2026-11-11", "duration_s": 604.8 },
  "channels": [
    { "id": "ch0", "label": "You" },
    { "id": "ch1", "label": "Remote" }
  ],
  "segments": [
    {
      "id": "s01",
      "start": 0.0,
      "end": 7.2,
      "channel": "ch1",
      "text": "Thanks for joining. Let's start with the billing migration.",
      "words": [
        { "w": "Thanks", "start": 0.0, "end": 0.52 }
      ]
    }
  ]
}
```

## Rules

- `version` must be `1`.
- `channels` must be non-empty with unique `id`s. Nothing outside this list may
  appear as a segment's `channel`.
- `segments` must be non-empty and sorted by `start`. Equal starts are allowed
  (simultaneous speech on two channels); reordering them is not.
- Every segment needs `end > start`.
- `words` is optional. When present, each word must lie inside its segment's
  `[start, end]`. Word timings are what make citations precise; the final
  recognition pass is expected to supply them.
- `text` must be non-empty. Whitespace-only is rejected.

## Why two channels, not one mixed stream

`ch0` is the microphone; `ch1` is the system loopback. They stay separate all the
way through. Mixing them would add room echo and keyboard noise to the cleanest
audio in the system — the remote participants' decoded stream — and would throw
away the free speaker attribution that comes with knowing which channel a word
arrived on.

Segments from both channels share one timeline, which is what lets the renderer
interleave them in the order they were spoken.

## Who writes it, who reads it

| Stage | Role |
|---|---|
| `mt` ASR adapter (ticket 03) | writes — one channel per run |
| merge (ticket 04) | reads two, writes one merged transcript |
| paragraph assembly | reads |
| note generation | reads |

`fixtures/transcript-sample.json` is a ten-minute synthetic meeting used by tests
and by the CLI demo. It is generated by `tools/build_fixture.py`; regenerate with
`python3 tools/build_fixture.py`. It is not a substitute for real meeting audio —
that arrives with the gold set in ticket 05.

## Compatibility

A change to this format increments `version`. Readers reject versions they do not
know rather than guessing, because silently misreading timestamps is worse than
refusing to run.
